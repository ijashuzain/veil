# Improve Veil Playback Before Replacing Providers

**Recommendation: retain CineSrc-backed Server5 as a bounded beta, fix its native playback state and controls first, and evaluate supported provider adapters without changing Servers1–4.** The strongest new discovery lead is **Flaxfer → Vidzee**, whose public consumer and demo code describe structured stream results, but it is not a verified native supplier or the fastest provider. MoviePlex is a genuine aggregation/player frontend with an internal resolver/proxy, yet the recorded anonymous resolver request returned **HTTP 403: restricted to authorized applications**; replacing CineSrc with its watch page has no demonstrated benefit. Directory screening covered **all 52 listed entry URLs: 42 non-blocking HTTP-200 landings, nine challenge/block pages and one timeout**, with zero newly verified native integrations. Historical simulator evidence supports keeping the existing Server5 baseline—seven titles played after resolver disposal, six passed seek/resume—but does not establish physical-device reliability or comparative performance. The practical path is a richer playback-session contract, coordinated controls, real subtitle/quality/episode support, and a small measured comparison before selecting a replacement. ([Directory](https://www.bestfreestreaming.org/sites/movies), [Vidzee demo](https://api.vz.raphsm4.dev), [MoviePlex resolver](https://api.movieplex.online/api/stream?tmdbId=1058424&type=movie&lang=en), [historical Server5 evidence](../docs/playback/server-five-native.md))

## MoviePlex exposes an internal resolver, but denies anonymous access

For `https://movieplex.online/watch/movie/1058424`, the recorded bundle inspection shows **a default custom HLS/MP4 player backed by `api.movieplex.online`, plus an alternate iframe player whose default provider is VidCore**. MoviePlex therefore is more than a CineSrc iframe skin. Its custom client expects source descriptors, subtitles, provider status and resolution metadata; sources can be direct upstream URLs or routed through MoviePlex’s proxy. This architecture was inferred from shipped client code, not captured during playback or verified against server implementation. ([Target watch page](https://movieplex.online/watch/movie/1058424), [application bundle](https://movieplex.online/assets/index-CMIFxJKg.js), [watch bundle](https://movieplex.online/assets/Watch-DeeiQPp_.js))

The decisive runtime observation was an anonymous GET to the observed resolver URL returning **HTTP 403** with `{"error":"Forbidden","message":"Access denied: MoviePlex API is restricted to authorized applications."}`. The client contains application-identification headers and a bundled key, but the research did not replay that key, spoof an origin or continue past the denial. **No playable MoviePlex source response, manifest, segment, MP4 range response, subtitle file or native handoff was obtained.** CORS-related response headers do not establish permission or compatibility for Veil. MoviePlex is consequently a conditional operator/API discussion, not an immediately usable replacement. ([Recorded endpoint](https://api.movieplex.online/api/stream?tmdbId=1058424&type=movie&lang=en), [client implementation](https://movieplex.online/assets/index-CMIFxJKg.js), [recorded response provenance](../research_notes/Veil%20streaming%20source%20evaluation/movieplex.md))

| Capability | Evidence in inspected MoviePlex code | Unresolved native requirement |
|---|---|---|
| HLS and MP4 | HLS.js/browser-native HLS branches and explicit MP4 handling | Actual usable media, codecs, headers, redirects and device decoding |
| DASH | No application DASH/MPD branch identified | Support not established |
| Subtitles and audio | External subtitle endpoint and VTT descriptors; HLS subtitle/audio track handling | Accessible files/tracks, language correctness, synchronization and native selection |
| Quality | HLS levels/dimensions plus provider/name/URL heuristics | Real renditions and decoded dimensions for the requested title |
| Episodes | Season/episode identity and navigation | Correct episode resolution and playback |
| Session lifetime | Proxy handling and several client-cache policies | Contractual expiry, refresh, cookie scope and IP binding |

The table describes static support, **not tested feature delivery**. In particular, MoviePlex defaults unknown quality to 1080 in one helper and can retain a 2160 preference while falling back to a “1080p FHD Master.” Its quality labels cannot certify source resolution. A separate metadata response for TMDB `1058424` identified **Hope (2026), IMDb `tt27369017`, quality CAM**; that is VidSrc’s metadata assertion, not MoviePlex’s source quality or evidence of playback. Likewise, MoviePlex’s seven-/30-minute source-cache thresholds and other resolver caches are client policies, not measured token lifetimes. ([Watch bundle](https://movieplex.online/assets/Watch-DeeiQPp_.js), [application bundle](https://movieplex.online/assets/index-CMIFxJKg.js), [VidSrc target metadata](https://vsembed.ru/info/movie/1058424.json))

Provider labels also require care: MoviePlex maps names such as PlexMax to VidZee/NXOCW, IMAX Digital to VidRock and Roxy Cinema to CineSrc. Recognition and ranking code do not prove those providers currently resolve this movie. Embedding MoviePlex’s CineSrc option would add an outer frontend around an existing provider, with no demonstrated startup or quality gain. Veil’s existing resolver explicitly accepts only HTTPS `cinesrc.st`, so changing its entry URL to MoviePlex would fail the host check rather than implement a new resolver. ([Alias and iframe implementation](https://movieplex.online/assets/Watch-DeeiQPp_.js), [Veil resolver cited by the notes](../lib/src/features/native_player/repository/cinesrc_stream_resolver.dart))

## Server5 has app-side defects a supplier cannot fix

The earlier simulator audit recorded all seven tested titles passing on Servers1–3 after fixes; Server4 varied with unavailable titles, denied media and changes between DASH and MP4 selection. The separate Server5 report recorded advancing native video **after the temporary resolver WebView was disposed** for all seven titles; Game of Thrones S2E3 stalled during seek/resume, while the other six passed. Those observations justify retaining a baseline, not certifying reliability. Earlier startup figures were single-network, route-entry measurements affected by provider/cache variability and a deliberate eight-second Play-gate delay on Server1; they are not a controlled Server5 comparison. ([Earlier embedded audit](../docs/playback/live-audit-2026-10-13.md), [earlier native matrix](../docs/playback/server-five-native.md))

The supplied source-inspection notes identify the following issues. These are recorded code findings rather than fresh reproduction of the user’s symptoms. ([Native strategy research](../research_notes/Veil%20streaming%20source%20evaluation/native-strategy.md))

| Concern | Recorded app-side finding | Practical consequence |
|---|---|---|
| Slow resolution/startup | Browser bootstrap and HLS capture precede native initialization; separate 35-second resolver and 25-second initialization limits | Limits are not observed latency. Add stage timing before attributing delay to provider or player. |
| Seek/skip responsiveness | Seek snapshots `isPlaying`, pauses, seeks, then conditionally resumes; overlapping commands lack a latest-target queue | Older work can override newer pause intent; repeated skips can collide or fail to accumulate. |
| Paused spinner | Spinner follows `isBuffering` regardless of desired play state | A readiness signal becomes misleading playback-wait UI. It does not by itself prove failed resume. |
| Pause feedback and controls | No explicit desired-playback state; no auto-hide state/timer; persistent header and tall bottom panel | Responsiveness and layout need app work regardless of supplier. Actual pause latency remains unmeasured. |
| Resolution, subtitles and audio | Minimal URL/format/headers/timestamp model; conservative AVC/unspecified-codec child playlist up to 720p where available; absent track/caption controls | Selection limits quality and can discard master-level alternate-track associations. UI cannot expose missing metadata. |
| Episode switching | Native screen receives entry URL and title rather than a structured request/catalog | Initial episode routing exists, but in-player episode navigation and lifecycle management are missing. |

The relevant implementation boundaries are the native view, stream model, resolver and launcher. Preserving a compatible HLS master would allow adaptive rendition discovery and retain associated audio/subtitle groups, but simply enabling every high-resolution or HEVC variant would discard the rationale for the historical compatibility fixes. ([Native view](../lib/src/features/native_player/view/native_player_view.dart), [stream model](../lib/src/features/native_player/models/resolved_stream.dart), [resolver](../lib/src/features/native_player/repository/cinesrc_stream_resolver.dart), [launcher](../lib/src/features/embeded_player/utils/playback_launcher.dart))

**Keep AVPlayer/Media3 ExoPlayer and use the installed stack’s existing capabilities first.** The notes record `video_player 2.14.1` with video/audio track and caption-file APIs. On iOS, the inspected plugin implements video preference through peak bitrate, not a guaranteed exact-resolution lock; subtitle-file rendering is also distinct from native segmented HLS subtitle discovery. Apple warns that exact, zero-tolerance seeking can add decoding delay and recommends serialized seeking toward the latest target. Finite tolerance is therefore a later tuning experiment, not a substitute for fixing command races or proof of a speedup. ([Recorded plugin analysis](../research_notes/Veil%20streaming%20source%20evaluation/native-strategy.md), [Flutter controller API](https://pub.dev/documentation/video_player/latest/video_player/VideoPlayerController-class.html), [Apple seek contract](https://developer.apple.com/documentation/avfoundation/avplayer/seek(to:tolerancebefore:toleranceafter:)), [Apple smooth-seeking guidance](https://developer.apple.com/library/archive/qa/qa1820/_index.html))

## Implement session-aware playback, then run a bounded comparison

The recommended boundary is **`PlaybackRequest → provider adapter → validated playback session → native controller`**, isolated within Server5. Preserve Server1 VidSrc/vsembed, Server2 CineJoy, Server3 CineSrc embed and Server4 VidLink target/launcher behavior. Retain explicit embedded fallback, but identify Server3’s CineSrc fallback accurately: it can recover browser-session compatibility without providing an independent upstream. Track actual source/provider identity when known so differently branded wrappers do not masquerade as diverse fallback sources. ([Playback targets](../lib/src/features/embeded_player/utils/playback_target.dart), [native strategy](../research_notes/Veil%20streaming%20source%20evaluation/native-strategy.md), [MoviePlex alias implementation](https://movieplex.online/assets/Watch-DeeiQPp_.js))

| Order | Proposed implementation | Acceptance evidence required |
|---|---|---|
| **P0: state and diagnostics** | Track desired play/pause separately; one in-flight seek plus latest target; accumulate skips against pending target; cancel stale work on close/retry/episode change. Instrument resolve, teardown, initialization, first frame, seek frame-ready and failures. | Latest pause wins; paused seeks stay paused; rapid taps reach accumulated/clamped target; stale completions cannot restart old playback. Distinguish command completion from rendered-frame readiness. |
| **P0: waiting UI and overlay** | Drive waiting UI from startup or requested playback waiting for media. Add compact timeline/transport, tap reveal and a proposed three-second auto-hide while playing. | Pausing dismisses playback-wait UI without re-resolution; controls remain accessible while paused, scrubbing, menu-open or accessibility-focused. |
| **P1: request/session model** | Carry content and episode identity, master URL, format/codecs, expiry/refresh, per-origin request policy, actual upstream identity, tracks, capabilities, cancellation and typed failures. | Complete usable session after resolver disposal; transient credentials remain in memory; history stores identity/preferences rather than expiring URLs. |
| **P1: quality and captions** | Preserve compatible adaptive masters; expose Auto and honest quality/audio preferences. Add declared sidecar captions, language/Off/default/forced handling and offset; add segmented HLS bridging only where needed. | Actual dimensions/track inventory verified; position and play intent preserved; subtitle synchronization survives seeking and quality changes; unavailable tracks reported honestly. |
| **P1: episodes and adapters** | Pass structured episode context, reuse catalog and per-episode history, cancel old resolution, and trial only candidates with supported native-session contracts. | Correct series/season/episode; no old audio/events; deliberate resume/next-episode policy; prompt source-aware failure or explicit server selection. |
| **P2: native tuning** | Profile finite seek tolerance, waiting reasons and bounded buffer/back-buffer controls. | Measured responsiveness improvement without unacceptable seek error, rebuffering or memory regression on physical devices. |

These are proposed next steps, not implemented changes or measured outcomes. They follow the concrete gaps in the supplied code analysis and existing native-player contracts. ([Implementation rationale and acceptance proposals](../research_notes/Veil%20streaming%20source%20evaluation/native-strategy.md), [Android seek parameters](https://github.com/androidx/media/blob/release/libraries/exoplayer/src/main/java/androidx/media3/exoplayer/SeekParameters.java), [Apple media selection](https://developer.apple.com/documentation/avfoundation/avplayer/setmediaselectioncriteria(_:formediacharacteristic:)))

A playback session must cover the **entire HLS request graph**—master and child playlists, segments, initialization maps, keys and subtitles—not only the first URL. Cookie scope and destination-specific headers need explicit handling; browser cookies do not automatically become a complete native session. Android offers request-dependent resolution through its data-source layer, while no equivalent blanket AVPlayer interception guarantee was established in these notes. Prefer direct CDN delivery when the supported session permits it; use a backend resolver for credential custody where required, and a media proxy only when concrete session binding or signing rules demand one. ([Apple cookie contract](https://developer.apple.com/documentation/avfoundation/avurlassethttpcookieskey), [Media3 customization](https://developer.android.com/media/media3/exoplayer/customization), [Media3 HLS](https://developer.android.com/media/media3/exoplayer/hls))

The existing Supabase proxy is not a ready-made session solution: the notes report limited upstream header forwarding, manual redirects without proxy-aware rewriting, `.m3u8` pathname-based playlist detection, commented-out host enforcement and no cookie/token-refresh contract. A selected proxy would need redirect-aware origin checks and URL resolution, MIME/body-aware playlist handling, keys/maps/subtitles, correct Range/206 and transformed response semantics, cancellation and bounded refresh. **No evidence establishes that blanket proxying improves startup or seeking.** ([Existing proxy cited by the research](../supabase/functions/proxy/index.ts), [recorded proxy assessment](../research_notes/Veil%20streaming%20source%20evaluation/native-strategy.md))

For the next evaluation, cap scope at **current CineSrc plus at most two candidates** that first establish supported native access, content/episode mapping, required headers, token TTL/refresh, track metadata, error/rate-limit behavior and integration/support terms. Vidzee is the first feasibility inquiry; MoviePlex qualifies only if supported access becomes available. The notes propose one engineer-day per candidate for initial contract feasibility, avoiding an open-ended collection of frontend scrapers. ([Candidate evidence](https://api.vz.raphsm4.dev), [MoviePlex access finding](https://api.movieplex.online/api/stream?tmdbId=1058424&type=movie&lang=en), [bounded evaluation proposal](../research_notes/Veil%20streaming%20source%20evaluation/native-strategy.md))

Use a controlled standards-compliant HLS fixture to isolate app defects, then reuse **Fall 2: Deadpoint, Interstellar, Dune: Part Two, Avatar, Breaking Bad S1E1, Game of Thrones S2E3 and Arcane S2E3** on physical iOS and Android under two network conditions. Two starts per title/platform/network produce **56 startup attempts per candidate**, a proposed screening matrix rather than completed work. Record cold/warm state, resolver and initialization time, actual first frame, failures, seek-to-frame, rebuffering, subtitle sync, quality changes and episode correctness. Include pause during seek, rapid skips, buffered/unbuffered seeking, background/resume, network changes, closure during resolution and a finalist session crossing documented expiry. ([Historical fixture matrix](../docs/playback/server-five-native.md), [proposed test protocol](../research_notes/Veil%20streaming%20source%20evaluation/native-strategy.md))

Initial targets in the notes—**≤100 ms control acknowledgment, ≤1 second warm/in-buffer seek, ≤3 seconds cold/out-of-buffer seek and ≤8 seconds native first frame**—are proposed budgets requiring calibration, not measured provider capabilities or release promises. The suggested ≥95% startup-success gate is likewise a small-screening acceptance rule, not proof of production reliability or a stable p95. Report failures and timeouts alongside medians, ranges and per-device/network counts. Select among candidates passing session and feature requirements by measured startup/seek recovery, then subtitle/quality/episode coverage, maintainability and delivery cost. If none qualifies, retain the beta and explicit fallback rather than declaring a fastest provider from one successful title. ([Evaluation budgets and limitations](../research_notes/Veil%20streaming%20source%20evaluation/native-strategy.md))

## Conclusion

The decision unit should be a **supported, refreshable playback session**, not a streaming-site brand or extracted URL. The directory is useful for finding upstream leads, but its many frontends do not establish many independent native suppliers. Separating app-state correctness from source-session correctness lets Veil improve controls immediately and judge future providers without attributing every stall to decoding or every quality label to a real rendition.

The remaining uncertainty is concrete: whether any shortlisted supplier can return a complete session that keeps working on physical iOS and Android through seeking, subtitles, episode changes and expiry. That evidence would justify replacing or supplementing CineSrc. Until it exists, the defensible decision is a bounded Server5 improvement and evaluation program—not a claim that MoviePlex, Vidzee or any of the 52 sites is already the best or fastest native provider.
